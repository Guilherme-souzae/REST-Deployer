## Message 1: User (Tue 10 Nov 2026, 10:00)

In this project, besides Jenkins running unit tests, I want to have a Newman that will run runtime tests of the API. How do I work with Jenkins and Newman together? Is it possible to make Jenkins create a Newman container, for example, make it run a series of tests and then collect a report generated by Newman?

## Claude

Yes, it is possible, and it is a very common pattern. The cleanest way is for Jenkins to run Newman as a disposable container (`docker run --rm`) mounting a workspace folder as a volume, so that the report generated inside the container shows up directly in the Jenkins workspace. Jenkins then publishes the report and sends it by e-mail.

#### How the pieces connect

1. Jenkins runs a stage that calls `docker run` with the official `postman/newman` image.
2. The container reads the collection (and the environment) from the workspace through a volume, runs the tests against the URL of the already-deployed API and writes the reports to `/etc/newman/reports` (or another mounted folder).
3. The container finishes and is removed. Newman's exit code decides whether the stage passes or fails.
4. In the `post` block, Jenkins archives the reports, publishes the JUnit results and sends the e-mail.

#### Prerequisite: Jenkins must be able to use Docker

Since Jenkins already runs in a container on your EC2 instance, it needs access to the host's Docker. The usual ways:

- Mount the socket in `docker-compose.yml`: `/var/run/docker.sock:/var/run/docker.sock`.
- Install the Docker CLI in the Jenkins image (in your Dockerfile).
- Give the `jenkins` user permission to use the socket (`docker` group).

This is the "Docker outside of Docker" pattern. It is worth citing in the paper as an architecture decision, together with the security trade-off: whoever has access to the socket has practically root on the host.

#### Important pitfall: volumes with Docker-outside-of-Docker

When Jenkins (inside a container) calls `docker run -v $WORKSPACE:/etc/newman`, **the path is resolved by the host's Docker, not by the Jenkins container**. So the `$WORKSPACE` path (something like `/var/jenkins_home/workspace/...`) must also exist on the host. Two solutions:

- Mount `jenkins_home` at the same path on both sides (for example `/var/jenkins_home:/var/jenkins_home`), so the path is identical on the host and in the container.
- Avoid volumes and use `docker cp` to copy the collection in and the reports out.

The first one is simpler.

#### Example stage in the Jenkinsfile

```groovy
pipeline {
    agent any

    environment {
        API_URL = credentials('deploy-api-url')   // or the host instance IP
    }

    stages {
        stage('Unit tests') {
            steps {
                sh 'pip install -r requirements.txt && python -m unittest test.py'
            }
        }

        stage('Deploy') {
            steps {
                // ssh to the host instance...
                echo 'deploy via SSH'
            }
        }

        stage('Wait') {
            steps {
                sleep time: 20, unit: 'SECONDS'
            }
        }

        stage('Newman runtime tests') {
            steps {
                sh '''
                    mkdir -p newman-reports
                    docker run --rm \
                      -v "$WORKSPACE/postman:/etc/newman/collections:ro" \
                      -v "$WORKSPACE/newman-reports:/etc/newman/reports" \
                      postman/newman:alpine run /etc/newman/collections/api.postman_collection.json \
                      --env-var baseUrl=http://${API_URL}:5000 \
                      --reporters cli,junit,htmlextra \
                      --reporter-junit-export /etc/newman/reports/newman.xml \
                      --reporter-htmlextra-export /etc/newman/reports/report.html
                '''
            }
        }
    }

    post {
        always {
            junit allowEmptyResults: true, testResults: 'newman-reports/newman.xml'
            archiveArtifacts artifacts: 'newman-reports/**', allowEmptyArchive: true
            publishHTML(target: [
                reportDir: 'newman-reports',
                reportFiles: 'report.html',
                reportName: 'Newman Report',
                keepAll: true
            ])
            emailext(
                subject: "[${currentBuild.currentResult}] ${env.JOB_NAME} #${env.BUILD_NUMBER}",
                body: "Report attached. Details: ${env.BUILD_URL}",
                to: 'your@email.com',
                attachmentsPattern: 'newman-reports/report.html'
            )
        }
    }
}
```

#### Points to note

- **HTML reporter:** Newman's default reporters (`cli`, `json`, `junit`) do not produce a nice HTML report. For that, use `newman-reporter-htmlextra`, which does not come in the `postman/newman` image. You have two options: use the `dannydainton/htmlextra` image, which already includes the reporter, or build your own image (`FROM postman/newman` + `npm install -g newman-reporter-htmlextra`) and publish it on Docker Hub, which fits well with the "Upload everything to Docker Hub" item of your plan.
- **Stage result:** Newman returns a non-zero code if any test fails, so the stage fails automatically. If you want the report to be generated and archived anyway, the `post { always { ... } }` block already covers it.
- **Required plugins:** `junit` (usually already present), `htmlpublisher` (for `publishHTML`), `email-ext` (for `emailext`) and the Docker Pipeline plugin, if you want to use the `docker.image().inside` syntax. This goes in your CasC file, in the plugin list.
- **Network:** if the API is on another EC2 instance, the Newman container only needs to reach its public or private IP. The API instance's Security Group must open the application port to the Jenkins instance's IP.
- **Waiting after the deploy:** instead of a fixed `sleep`, you can use a `curl` health-check loop until the API answers, which is more robust and is good to cite as an improvement.

#### Alternative: Docker agent

Jenkins lets you declare the container as the stage agent:

```groovy
stage('Newman') {
    agent {
        docker {
            image 'postman/newman:alpine'
            args '--entrypoint=""'
        }
    }
    steps {
        sh 'newman run postman/api.postman_collection.json -r cli,junit --reporter-junit-export newman.xml'
    }
}
```

It is shorter, but it requires the Docker Pipeline plugin and `--entrypoint=""` because of the Newman image's entrypoint. For the paper, the explicit `docker run` is usually better, because you show and explain each part of the process.

#### For the text of the paper

This section yields a good part of the discussion for "Newman test configuration": why test at runtime after the unit tests (unit tests validate the isolated logic, Newman validates the deployed system, with real network, configuration and integration), why run Newman in a container (reproducibility, no need to install Node on Jenkins) and the problem of volume paths with Docker-outside-of-Docker, which shows technical understanding beyond the basic tutorial, something the rubric values.

If you want, I can build the Dockerfile of the custom Newman image with htmlextra, or review your `docker-compose.yml` and the CasC to include Docker access and the required plugins.

## Claude

Yes, two things are missing: the host's Docker socket and the Docker CLI inside the image. In addition, your `jenkins_home` volume needs to be adjusted because of the path pitfall I mentioned.

#### 1. Mount the Docker socket

In `docker-compose.yml`, add the socket and access to the host's `docker` group:

```yaml
services:
  jenkins:
    build:
      context: .
      dockerfile: Dockerfile
    image: meu-jenkins:dev
    container_name: jenkins-local
    restart: unless-stopped
    user: root   # see note below
    ports:
      - "8080:8080"
      - "50000:50000"
    environment:
      ADMIN_USER: "CHANGEME"
      ADMIN_PASSWORD: "CHANGEME"
    volumes:
      - /var/jenkins_home:/var/jenkins_home      # bind mount, same path on the host and in the container
      - ./casc:/var/jenkins_casc:ro
      - /var/run/docker.sock:/var/run/docker.sock
```

Or, instead of `user: root`, which is the simplest option but less secure, use `group_add` with the GID of the host's docker group (find it with `getent group docker | cut -d: -f3`):

```yaml
    group_add:
      - "999"   # replace with the GID of the docker group on your EC2
```

In that case Jenkins keeps running as the `jenkins` user, but with permission to use the socket. This is the option I recommend.

#### 2. Install the Docker CLI in the image

The Jenkins container needs the `docker` client (not the daemon). In your Dockerfile:

```dockerfile
FROM jenkins/jenkins:lts-jdk17

USER root
RUN apt-get update && \
    apt-get install -y --no-install-recommends docker.io && \
    rm -rf /var/lib/apt/lists/*
USER jenkins

# ... rest of your Dockerfile (plugins, CasC etc.)
```

Debian's `docker.io` package installs the client and the daemon, but only the client will be used, since the daemon is the host's. If you prefer a smaller image, you can install only `docker-ce-cli` from Docker's official repository, but that takes more lines (adding the GPG key and the repository).

#### 3. The jenkins_home volume

This is the subtle point. In your current compose, `jenkins_home` is a named volume, whose real path on the host is under `/var/lib/docker/volumes/...`. When Jenkins runs `docker run -v $WORKSPACE/postman:/etc/newman/...`, the host's Docker will look for `/var/jenkins_home/workspace/...` **on the host**, where that path does not exist, and will create an empty folder, making Newman unable to find the collection.

That is why I suggested the bind mount `/var/jenkins_home:/var/jenkins_home`: the path is identical on both sides. Two details:

- Create the folder on the host and give ownership to UID 1000 (the `jenkins` user of the official image):
  ```bash
  sudo mkdir -p /var/jenkins_home
  sudo chown -R 1000:1000 /var/jenkins_home
  ```
- If you already have data in the current named volume and want to keep it, you must copy it first. If it is a new environment, ignore this.

With this, the `volumes: jenkins_home:` block at the end of the file is no longer needed and can be removed.

#### 4. Test

After `docker compose up -d --build`:

```bash
docker exec -it jenkins-local docker ps
docker exec -it jenkins-local docker run --rm hello-world
```

If the first command lists the host's containers without a permission error, it is working. If you get `permission denied` on the socket, the GID in `group_add` is wrong.

#### 5. Plugins in CasC

In your plugin file (`plugins.txt` or equivalent), include:

```
docker-workflow
junit
htmlpublisher
email-ext
```

`docker-workflow` is only needed if you use the `agent { docker { ... } }` syntax. For `docker run` through `sh`, it is not needed.

#### Security note for the paper

Whoever controls the Docker socket has, in practice, root access to the host, because they can start a privileged container mounting `/`. Since Jenkins executes the code of the `Jenkinsfile` from the repository, anyone who can change that file can, in theory, run commands on the host. In your project this is acceptable (study environment, own repository, restricted Security Group), but it is worth recording as a known risk and citing production alternatives, such as separate Jenkins agents, rootless Docker or Kaniko/Podman. This fits well in the critical discussion section that the rubric values.

How do I create a basic Newman collection to test the API?

*[Claude created `api.postman_collection.json`, validated that the JSON was well-formed, and sent it as a file.]*

I created the file `api.postman_collection.json`, a basic collection in Postman v2.1 format that Newman runs directly. The JSON was validated, but it has not yet been run against a real API. The routes (`/health` and a CRUD for `/items`) are generic, so you need to adapt them to your Flask API.

#### Collection structure

The collection has six requests in sequence, forming a complete flow:

1. **Health check**: `GET /health`, checks status 200 and a response time under 500 ms.
2. **List items**: `GET /items`, checks the status, a JSON `Content-Type` and that the body is a list.
3. **Create item**: `POST /items`, checks status 201 and stores the returned `id` in the `itemId` variable.
4. **Get created item**: `GET /items/{{itemId}}`, confirms that the id matches the one created before.
5. **Delete item**: `DELETE /items/{{itemId}}`, accepts 200 or 204.
6. **Nonexistent item returns 404**: repeats the GET and expects 404, proving that the deletion worked.

#### Important points

- **`baseUrl` variable:** the default value is `http://localhost:5000`, but in the pipeline you override it with `--env-var baseUrl=http://EC2_IP:5000`, as in the Jenkinsfile stage we built earlier.
- **Chaining between requests:** `pm.collectionVariables.set('itemId', ...)` passes the id from request 3 to the following ones. Order matters, because Newman runs the requests in the order of the file.
- **Tests are JavaScript:** each `pm.test(...)` block becomes a case in the JUnit report. If a `pm.test` fails, Newman returns a non-zero code and the Jenkins stage fails.

#### How to adapt it to your API

- Replace the paths and request bodies with the real endpoints.
- Adjust the expected statuses to what Flask returns (for example, if your POST returns 200 instead of 201).
- If the API has no `/health`, create a simple route that returns `{"status": "ok"}`. It also serves for the post-deploy wait loop and for the status front end that you listed as an additional feature.

#### Test locally before going to Jenkins

With the API running on your machine:

```bash
docker run --rm --network host \
  -v "$(pwd):/etc/newman" \
  postman/newman:alpine run api.postman_collection.json
```

`--network host` only works on Linux. On Windows or Mac, use `--env-var baseUrl=http://host.docker.internal:5000`. Once it passes locally, put the file in the repository's `postman/` folder, which is the path used in the Jenkinsfile.

## Message 4: User (Wed 11 Nov 2026, 18:47)

ok, how do I make this collection have an IP into which a credential stored in Jenkins will be injected?

## Claude

The collection does not need to know the IP. It only uses `{{baseUrl}}`, and Jenkins injects the value when running Newman. The full path has three parts.

#### 1. Create the credential in Jenkins

Create a **Secret text** credential with a fixed ID, for example `deploy-host-ip`, and the IP of the API's EC2 as the value. Since you use CasC, you can declare it in the YAML, reading the value from an environment variable of the container:

```yaml
credentials:
  system:
    domainCredentials:
      - credentials:
          - string:
              scope: GLOBAL
              id: "deploy-host-ip"
              description: "IP of the instance that hosts the API"
              secret: "${DEPLOY_HOST_IP}"
```

And in `docker-compose.yml`:

```yaml
    environment:
      DEPLOY_HOST_IP: "${DEPLOY_HOST_IP}"   # comes from a .env file kept out of Git
```

This way the IP is not in the repository. If you prefer, you can also create the credential manually through the interface, under *Manage Jenkins → Credentials*.

#### 2. Inject it in the Jenkinsfile

The most explicit way is `withCredentials`, which limits the variable to the block:

```groovy
stage('Newman runtime tests') {
    steps {
        withCredentials([string(credentialsId: 'deploy-host-ip', variable: 'DEPLOY_HOST')]) {
            sh '''
                mkdir -p newman-reports
                docker run --rm \
                  -v "$WORKSPACE/postman:/etc/newman/collections:ro" \
                  -v "$WORKSPACE/newman-reports:/etc/newman/reports" \
                  postman/newman:alpine run /etc/newman/collections/api.postman_collection.json \
                  --env-var baseUrl=http://$DEPLOY_HOST:5000 \
                  --reporters cli,junit \
                  --reporter-junit-export /etc/newman/reports/newman.xml
            '''
        }
    }
}
```

The shorter alternative is `environment { DEPLOY_HOST = credentials('deploy-host-ip') }` at the top of the pipeline, but then the variable is available in all stages. `withCredentials` follows the principle of least privilege, and it is worth citing that in the paper.

#### 3. How the value reaches the collection

`--env-var baseUrl=...` defines a Newman environment variable, which takes precedence over the collection variable `baseUrl` (the default `localhost:5000` in the file). The `{{baseUrl}}` of all the requests then points to the EC2.

#### Important details

- **Use single quotes in `sh '''...'''`.** This way the shell expands `$DEPLOY_HOST`, not Groovy. With double quotes, Jenkins warns that it is interpolating a secret, and it can leak into the build history.
- **Jenkins masks the value in the logs.** Your IP will appear as `****` in the console, which is expected and confirms that the injection worked. To debug, test with `curl` outside the pipeline.
- **An IP by itself is not a critical secret.** But keeping the IP as a credential avoids leaving it in the repository and reuses the same value in the deploy stage and in Newman. This is a great example for the "Configuring Jenkins credentials" chapter of your draft.
- **For the deploy SSH key**, use another type of credential, **SSH Username with private key** (`sshUserPrivateKey`), and the `ssh-agent` plugin for the deploy stage.

#### Alternative: environment file

If the collection comes to have several variables (port, tokens, test user), instead of several `--env-var` you can store a Postman `environment.json` file as a **Secret file** credential and pass it with `-e`:

```groovy
withCredentials([file(credentialsId: 'newman-env', variable: 'NEWMAN_ENV')]) {
    sh 'docker run --rm -v "$NEWMAN_ENV:/etc/newman/env.json:ro" ... run ... -e /etc/newman/env.json'
}
```

For a single variable, `--env-var` is simpler.

## Message 5: User (Wed 11 Nov 2026, 18:49)

where do I store this collection JSON file?

## Claude

Store the collection **in the project's own Git repository** (REST-Deployer), in a `postman/` folder at the root. It is not a secret, it is test code, so it should be versioned together with the API.

#### Suggested structure

```
REST-Deployer/
├── main.py
├── test.py
├── requirements.txt
├── Dockerfile
├── Jenkinsfile
└── postman/
    └── api.postman_collection.json
```

The path `postman/api.postman_collection.json` is exactly what the Newman-stage Jenkinsfile already expects.

#### How it reaches Newman

1. The GitHub webhook triggers the pipeline.
2. Jenkins fetches the `Jenkinsfile` and checks out the whole repository into the workspace (`/var/jenkins_home/workspace/<job>`). In a *Pipeline from SCM* job this is automatic. With a separate stage, the command is `checkout scm`.
3. `docker run -v "$WORKSPACE/postman:/etc/newman/collections:ro"` mounts that folder inside the Newman container.

That is why the bind mount `/var/jenkins_home:/var/jenkins_home` that we adjusted in the compose is essential. Without it, the host's Docker does not find the `postman/` folder and Newman fails with "collection file not found".

#### Why in the repository and not elsewhere

- **Versioning:** the collection evolves together with the API. A commit that adds an endpoint can add the corresponding test.
- **Reproducibility:** anyone who clones the repository runs the same tests, locally or in the pipeline.
- **No manual step:** there is no need to copy the file to the Jenkins EC2.
- **Credentials only for what is secret:** the IP goes as a Jenkins credential, the collection does not.

#### Alternatives (and why not)

- **Inside the Newman Docker image:** you can do `COPY postman/ /etc/newman/` in your custom image and publish it on Docker Hub, but then every test change requires an image rebuild and push. It is only worth it if you want a self-contained test image.
- **In a Secret file credential:** this only makes sense for the *environment* file if it has tokens or passwords. For the collection, no.
- **Manually in the `jenkins_home` volume:** it works, but the file leaves version control and breaks reproducibility.

#### Care when exporting from Postman

- Export as **Collection v2.1** (the format of the file I generated already is).
- Do not leave **tokens, passwords or real IPs** in variables with a current value in the exported file. If the collection goes to a public repository, this becomes a leak. Leave the `baseUrl` variable with a harmless default value (`localhost`) and inject the real one through Jenkins.
- If you keep an environment file with real data, put it in `.gitignore`.
